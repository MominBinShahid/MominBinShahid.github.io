I rebuilt this site. It is the personal one I put together for myself years ago, and I had outgrown what it could do. I wanted somewhere I would actually write, and a résumé page that does not go stale the moment I edit the document it came from. The old one ran on Gatsby 2, three majors behind Gatsby itself, and Gatsby itself is a story we will get to. The new one runs on Astro 7. The framework swap was the easy part. It usually is. Astro's components are JSX-shaped, so my React instincts transferred straight over, and markdown stayed markdown.

There is a joke here I should make before anyone else does. I built this site with a complete blog attached. An index, tag pages, a feed advertised in the config. Then I never wrote a post. `/blog/` has been live for years, returning a cheerful 200 and listing nothing. So the first thing I have ever actually written for this site is this, the post about replacing it. It turns out what I needed was never a writing habit. It was a migration.

Then I compared what the old build actually shipped against what was in the repo, and spent longer on that than on everything else combined. The hard part of a migration is never the framework. It is finding everything the old framework was quietly doing for you, because none of it is written down anywhere you would think to look.

## Nobody sends a memo

Nobody announces that a framework is winding down. The Gatsby repo is not archived. The docs are up. There are 55,939 stars, 450 open issues, and no deprecation notice anywhere. There is no announcement to link to; you work it out from the commit log. I used to read documentation for fun. Now, apparently, I read commit histories for omens, which turned out to be the same skill the rest of this migration needed.

The last release of the `gatsby` package was 5.16.1, in February, seven months before this post. In the twelve and a half months before I checked, the repo took 122 commits, and 87 of them were bots.[^1] Of the 35 human commits, two people wrote 25. I am not going to tell you Gatsby is dead. It was genuinely good, and I built on it happily for years. I will tell you that dependabot is currently its most prolific contributor, and let you draw the graph yourself.

## The file that wasn't mine

The scariest find was `robots.txt`, and not because of this site. It was generated by `gatsby-plugin-robots-txt` and existed on no branch, only in build output. This is what was live:

```txt
User-agent: *
Allow: /
Sitemap: https://MominBinShahid.github.io/sitemap.xml
Sitemap: https://MominBinShahid.github.io/MealUnits/sitemap.xml
Host: https://mominbinshahid.github.io
```

The second sitemap line is the load-bearing one. My origin hosts another app at `/MealUnits/`, an offline insulin calculator. Crawlers read `robots.txt` only from the origin root, so the copy inside `/MealUnits/` never gets fetched; this root file held that app's only crawl entry. Ship the new site without recreating it and I break search for a site I was not even migrating, and nothing fails visibly. No error, no red build. Just a slow, quiet drop out of search results while I congratulate myself on the launch.

## One plugin, ten files

`gatsby-plugin-manifest` was a single entry in `gatsby-config.plugins.js`, with `legacy: true` set. From one tracked image, `src/images/logo.png`, it generated eight icon PNGs, a `/favicon-32x32.png` referenced in every page's `<head>`, a `/manifest.webmanifest`, a `theme-color` meta tag, and eight `<link rel="apple-touch-icon">` tags. The input was in git. None of the outputs were.

| URL the browser asks for | Made by | In git? | After a naive cutover |
| --- | --- | --- | --- |
| `/favicon-32x32.png` | `gatsby-plugin-manifest` | No | 404 |
| `/icons/icon-48x48.png` and seven siblings | `gatsby-plugin-manifest` | No | 404 |
| `/manifest.webmanifest` | `gatsby-plugin-manifest` | No | 404 |
| `/robots.txt` | `gatsby-plugin-robots-txt` | No | Gone, and nothing complains |
| `/sw.js` | `gatsby-plugin-offline` | No | Worse than gone. See below |
| `src/images/logo.png` | me, once, in 2024 | Yes | Fine, and nothing references it |

Remove the plugin and the favicon 404s on every page. Not a disaster on its own, but the shape of it is: the repo held one file, the live site held ten, and the mapping between them lived in a plugin I configured once and never thought about again.

## The underscore problem

GitHub Pages pipes your output through Jekyll by default, and Jekyll skips every path that starts with an underscore. Astro's default assets directory is `_astro`, which is where every hashed stylesheet and script lands. Without a zero-byte `.nojekyll` file at the root, that whole directory is dropped and the site serves bare, unstyled HTML.[^2] Gatsby never used underscore paths, which is exactly why I had never needed the file and would never have thought of it. The fix is the least dramatic thing in this post:

```sh
touch public/.nojekyll
```

The lesson is not the file. The lesson is that not having had a problem for years is not the same as understanding the system.

## The worker that outlived the site

`gatsby-plugin-offline` registered a service worker at `/`, and a worker with scope `/` sees the whole origin, `/MealUnits/` included.

![Diagram of one browser origin containing two apps side by side: this site at the root and MealUnits at /MealUnits/. A dashed boundary labelled "service worker registered at slash" encloses both of them, and a double-headed arrow labelled caches.keys() spans the full width underneath, showing that the call reaches every cache on the origin rather than only this app's.](../../assets/blog/sw-scope.svg)

Deleting the worker from the build does not delete it from anyone's browser. Returning visitors would keep getting a cached copy of a site that no longer exists, served forever by a ghost. The only way out is to ship a new worker at the same URL that takes over and removes itself.

Writing that replacement had its own trap. `caches.keys()` is origin-wide, so the obvious cleanup, delete everything and start fresh, would have wiped MealUnits' cached data too. That app is an insulin calculator people use offline, which is not something I get to break for tidiness. So the delete list is an allowlist of my own cache prefixes, never a denylist of ones to keep. A denylist is wrong the moment a third thing appears on the origin.

```js
const DELETE_PREFIXES = ['gatsby-plugin-offline', 'workbox-'];

self.addEventListener('activate', (event) => {
  event.waitUntil((async () => {
    const names = await caches.keys();
    const ours = names.filter((name) => DELETE_PREFIXES.some((p) => name.startsWith(p)));
    await Promise.all(ours.map((name) => caches.delete(name)));
    await self.registration.unregister();
  })());
});
```

I left IndexedDB alone too, and at the time that was caution rather than knowledge. I did not know what the other app stored or under what name, so I did not touch any of it. Then I went and asked. MealUnits opens a database called `MealUnits`, and it holds the only copy of the user's prescription, their injection log and their readings. No server, no account, no backup. The keys the old worker left behind are a few kilobytes of nothing. Caution turned out to be worth a great deal more than I thought I was buying.

## The dark mode that fought back

Not everything I found was infrastructure. The old dark mode was one line in `src/styles/dark.less`: `filter: invert(92%) hue-rotate(180deg) !important`, applied to the entire page. It works, sort of, and then every image and every emoji is inverted too, so each one needs a counter-filter, and the codebase grew a literal `<emoji>` element whose only job was to carry one:

```less
emoji {
  filter: invert(92%) hue-rotate(180deg) brightness(1.2) contrast(1.1) saturate(1.3) !important;
}
```

One shortcut, then a family of workarounds to prop it up. The new site uses `light-dark()` under `color-scheme: light dark`, so anyone following their OS preference gets the right theme from pure CSS, no JavaScript, no flash.

## What the build knew that I didn't

Every find above came from the same move: list every URL the old build emitted and compare it against the repo. Not memory, and not the config, because the config is a statement of intent, not of output. Mine advertised an RSS feed at `/rss.xml`. No plugin ever generated one. It 404'd for years and nobody noticed, including me. The new site has a real feed at that URL now, so the config and reality finally agree.

One more, found the same way and too good to leave out. My `.gitignore` had a line reading `Icon?`, which any Mac user will recognise: it hides the custom-folder-icon file, which is genuinely named `Icon` followed by a carriage return. But `?` matches any single character, and `core.ignorecase` is on by default on macOS. So `Icon?` also matches a directory called `icons`, and all eight touch icons I had just finished regenerating were being left out of every commit. They were on disk. The build reads the disk, so the build was fine. Only `git` disagreed, and only when I asked it directly.[^3]

I want to be honest about the "not memory" part, because I was my own counterexample twice. I said, twice, that the old `<head>` had nine `apple-touch-icon` links. There were eight. I only found out by enumerating the live HTML instead of trusting myself. Later I confidently explained a visual difference between two emoji as a CSS filter effect, and it was nothing of the sort; they were two different artwork generations. A filter recolours pixels. It cannot add a monitor that was never in the artwork. Both times I sounded certain, and both times the certainty was worth exactly nothing until I checked.

> A file in a repo survives a framework change. A file emitted by a plugin does not.

That is the whole migration in two sentences. Astro was pleasant and mostly unremarkable, which is about the highest compliment I can pay a framework. The real work was archaeology: walking the output of a build system on its way out and asking, of every file, who made you, and who makes you next time. Do that first. The swap itself can wait. It is the easy part.
