Your pull request is deploying to production

12 sep 2026 · 6 min read #Node.js#javascript

There's a moment, on every team that switches to continuous deployment, when the phrase pull request quietly changes meaning. It used to be a request: please look at this, tell me what you think, we'll ship it later — together, carefully. Then the pipeline gets good enough, and one Tuesday you realise the truthful name would be deploy request. Approve this, and it is in production in eleven minutes.

Nobody announces the shift. The YAML doesn't care what you call it. But everything about how you write, review, and split your work should change the day merge stops meaning "saved for later" and starts meaning "live".

Review for blast radius, not style

Code review used to carry two jobs at once: catch the things that would embarrass us, and negotiate the things we disagree about. The first job now belongs to machines — the linter, the formatter, and the type checker are faster than you and never get tired of arguing about semicolons. What's left for humans is the part machines are still bad at: consequences.

Here is what I actually read in a PR now, in order:

  • The migration, before any code that touches it. Is it expand-only? Can yesterday's code run against tomorrow's schema, because for four minutes it will?
  • The flag. What default does it ship with, who can flip it, and what does off look like?
  • Timeouts and retries on anything that crosses a network. An approved PR with an unbounded retry is an incident with a green tick on it.
  • The rollback story. If we revert this commit in a hurry, does the revert deploy clean?
  • And last — genuinely last — the code itself.

Style comments still happen, but as suggestions, never blockers. A nit has never paged anyone at 3 a.m. An unbounded retry has.

The pipeline is short on purpose

Ours fits on one screen, and that's a feature. Every stage you add to a pipeline is a stage somebody will want to skip during an incident, so each one has to pay rent:

# deploy.yml — runs on every merge to main
name: deploy
on:
  push:
    branches: [main]

concurrency:
  group: production
  cancel-in-progress: false   # never kill a deploy midway

jobs:
  ship:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci && npm test
      - run: npm run build
      - run: ./scripts/deploy.sh   # blue/green, ~4 minutes
      - run: ./scripts/smoke.sh    # the five endpoints that pay rent

Blue/green swap, then a smoke test that hits the five endpoints that actually earn the company money. Not five hundred assertions — five requests. If search, booking, payment, confirmation, and login answer correctly, the deploy is probably fine. If they don't, nothing else matters anyway.

Ship changes that can land alone

The pipeline is the easy half. The real discipline lives in the changes themselves, because a change that deploys the moment it merges has to be safe on its own — not safe once the other three PRs land. That means expand-and-contract for anything touching data (add the new column, write to both, read from new, drop the old — four boring PRs instead of one exciting one), and it means flags for anything touching behaviour:

// the feature is merged; the launch is a config change
if (flags.isEnabled('new-fare-cache', { user })) {
  return fareCache.lookup(query);   // new path, 2% of traffic
}
return legacySearch(query);          // old path stays warm

The feature is merged; the launch is a config change. Keeping those two sentences decoupled is most of the craft. Merging becomes routine, launching becomes deliberate, and neither one has to be scary.

The rule underneath all of this isn't technical. I've written it elsewhere and it keeps being true:

Both have taught me that great software is about understanding people, not just writing code 💡 — the thing every pipeline is actually made of

When it goes wrong — and it will

Continuous deployment doesn't mean fewer mistakes. It means cheaper ones. A bad deploy on a weekly release train is a crisis; a bad deploy on a pipeline like this is a revert that's live before the incident channel finishes arguing about who owns it. Two habits make that true in practice, not just in the slide deck:

  • Revert first, understand later. The broken commit is not a crime scene that needs preserving — production is.
  • A deploy isn't done when the pipeline goes green. It's done when the dashboards have been boring for ten minutes.

We ship a travel product, which means our rush hour is other people's Friday evening. The pipeline doesn't know that. The team does — and that's the correct place for that knowledge to live: in people who can decide this one can wait until the morning, on top of a system that never requires them to.

The part that actually took months

Building the pipeline took two weeks. Trusting it took the better part of a year, and that work was entirely human: convincing careful engineers that small-and-continuous is safer than big-and-ceremonial, sitting with someone through their first same-day merge, resisting the committee that wants to add a manual approval step back "just for now". The YAML was never the hard part.

But watch an engineer merge their first Tuesday-afternoon change, see it live before their tea goes cold, and go home on time — that's the payoff. Your pull request is deploying to production. Write it like you mean it.
