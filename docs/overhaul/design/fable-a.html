Getting Gatsby 2 to build on Apple Silicon

mar 2021 · 6 min read · gatsby.js node.js

New machine, old site. I cloned this blog onto an M1 MacBook, ran yarn install, and watched node-gyp produce a scroll of C++ errors longer than the site's entire source. The culprit was three levels deep in the dependency tree: node-sass, a package that compiles native LibSass bindings at install time, pinned to a version that predates Apple Silicon and has never heard of arm64.

Gatsby 2 doesn't depend on node-sass directly. It arrives through gatsby-plugin-sass, which for this generation of the framework assumes the native implementation. On an Intel Mac that assumption costs you a slow install. On an M1 it costs you the build.

01 — The advice I refused

Every GitHub thread about this ends the same way, usually within four comments:

“Just install Rosetta 2 and run the x64 build of Node. Works fine.” — every thread, eventually

And it does work fine — that's the problem. Rosetta doesn't fix your toolchain, it hides it. From that day forward, every native module you compile is quietly built for the wrong architecture, every benchmark lies to you by thirty percent, and you will not find out until something segfaults in a way no search result has ever seen. The first thing I did on this machine was verify Node itself was native, and I wasn't about to break that seal for a Sass compiler:

terminalzsh
$ file "$(command -v node)"
/opt/homebrew/bin/node: Mach-O 64-bit executable arm64

$ node -e 'console.log(process.arch)'
arm64

file(1) is the tool I trust here, not the package manager's word. If the binary doesn't say arm64, nothing downstream of it counts.

02 — Three ways out

In ascending order of self-respect:

  1. Install Rosetta and run an x64 Node. Fast, popular, and it plants a translation layer under every build you'll do for years. No.
  2. Upgrade to Gatsby 3. Correct in the long run, but this is a personal site and that migration is a weekend I didn't have — and it still wouldn't remove node-sass from the tree on its own.
  3. Evict node-sass entirely and hand the plugin Dart Sass, which is pure JavaScript. Nothing native, nothing for node-gyp to compile, nothing that cares what your CPU is called.

03 — The fix

Dart Sass ships as the sass package with a node-sass-compatible API, and gatsby-plugin-sass accepts an implementation option. Two lines of config, and the native dependency's entire reason to exist disappears:

gatsby-config.jsjavascript
// Dart Sass instead of node-sass: pure JS, no native
// bindings, nothing for node-gyp to compile.
{
  resolve: "gatsby-plugin-sass",
  options: {
    implementation: require("sass"),
  },
},

Then remove the old package, add the new one, and make sure nothing transitive drags node-sass back in:

terminalzsh
$ yarn remove node-sass && yarn add -D sass
$ yarn why node-sass
=> This package doesn't seem to be present in your lockfile

$ yarn develop
success Building development bundle - 14.227s

Fourteen seconds, native, no translation layer. The styles compiled byte-identical — LibSass and Dart Sass disagree on a few edge cases, but none of them live in this stylesheet.

04 — Leave the campsite cleaner

I could have stopped there, but the Boy Scout Rule applies to dependency trees too. Before closing the terminal I pinned the Node version in .nvmrc, noted the implementation trick in the README for whoever clones this on the next unfamiliar CPU, and filed the Gatsby 3 migration as an issue instead of a guilt. The build is native, the tree is one native module lighter, and file(1) agrees with me on every binary in the chain. ■
