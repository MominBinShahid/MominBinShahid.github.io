# Post-deploy verification

Every URL and every piece of `<head>` markup the current Gatsby build puts on the origin,
enumerated live on 2026-09-21 — not from memory. Run this after the Astro cutover and
compare. Anything that was 200 before and is 404 after is a regression unless this file
says otherwise.

The rule this exists to enforce: **a file in a repo survives a framework change; a file
emitted by a plugin does not.** Almost everything below is plugin-emitted.

## One command

```sh
bash docs/overhaul/verify-deploy.sh                      # defaults to the live origin
bash docs/overhaul/verify-deploy.sh http://localhost:4321 # or a local Astro preview
```

## `.nojekyll` — yes, and it is the one that would break everything

GitHub Pages pipes the published output through Jekyll by default, and Jekyll **skips every
file and directory whose name starts with an underscore**. An empty `/.nojekyll` file turns
that off.

This matters far more under Astro than it did under Gatsby. Astro's default `build.assets`
is **`_astro`**, so every hashed stylesheet and script lands in `/_astro/`. Without
`.nojekyll` that whole directory is dropped and the site serves bare unstyled HTML with no
JavaScript — a total visual failure that still returns 200 on the page itself, so a
homepage smoke test would not catch it.

Gatsby happened not to use underscore paths, which is why this has never bitten. It would
bite immediately on cutover. It is a zero-byte file at the repo root.

## Social card

`og:image` and `twitter:image` both point at
`/static/<hash>/<hash>/momin.jpg` — a content-hashed artifact of `gatsby-plugin-sharp`.
The source `src/images/momin.jpg` **is tracked**, so the picture survives; the URL will not.
Anything that cached the old URL (LinkedIn, X) re-scrapes on its own schedule.

Separately on `og:title`: the homepage currently reports `"About"`. That is **correct
today** — the current homepage *is* the about page, so the tag is accurate, not a bug
(Momin's correction, 2026-09-21). It stops being correct the moment the new homepage is
something else, so it is a new-build task, not a fix to the old one.

New social cards are also a new-build item: the current card is `src/images/momin.jpg`
served through `gatsby-plugin-sharp`, and it predates the new look entirely.

## What this file deliberately does not cover

Hashed JS bundles (`/app-*.js`, `/framework-*.js`, `/webpack-runtime-*.js`, the six
vendor chunks) and `/page-data/**`. They are Gatsby-internal and are *supposed* to vanish.
Listing them as regressions would be noise.

## Added 2026-09-21 — behaviour, not files

Enumerating URLs does not catch everything. This one lived in a React component.

### `/mealunits/` must still correct its own casing

GitHub Pages serves a project site at its repository's **exact** case, so
`mominbinshahid.github.io/mealunits/` never reaches MealUnits. It falls through to the
user site and lands on this origin's 404 page, which rewrites the casing and redirects.

That fix has been live and verified since 2026-09-13. It existed only inside
`src/pages/404/index.jsx` in the Gatsby code, so a framework swap drops it with no
error, no 404 in a URL sweep, and nothing visibly wrong.

Ported to `src/lib/canonical-project-path.ts`. `verify-deploy.sh` now checks the built
404 page carries it.

Two details that must survive any rewrite of that file:

1. Only a first path segment that case-insensitively matches a **listed** project is
   rewritten, so every other 404 still renders as a 404.
2. It returns `null` when the casing is already correct. That is what stops the redirect
   loop, and it is not a truthiness check.

### The stale-worker caveat when testing the cutover

Per MealUnits' `docs/BLOG-FIX.md`: the maintainer's own browser is the **most** likely to
be holding the old service worker, so a clean profile is the one place the real exposure
path does not show up. Test the cutover from a browser that has actually visited the old
site, not a fresh one.
